# ADR 0017: Pushed request storage and browser binding

Status: Implemented application/storage foundation · 2026-10-18 · Public PAR and object consent remain pending

## Decision and ownership

Continue the mandatory PAR/RAR contract from ADRs 0012/0015 through the existing authorization bounded context. `domain/authorization.PushedRequest` owns an immutable typed request, its policy revision, a maximum 90-second reference lifetime and a one-use transition into a browser authorization workflow. It requires nonempty object authority and the existing explicit resource/permission/S256 request profile, with at least 16 bytes of client state. The client must generate unpredictable state; a length check cannot prove entropy. A workflow gets its own five-minute deadline after valid reference consumption.

`services/authorization.Push` validates the exact registered client/resource/type/action vocabulary before requesting entropy. `BeginPushed` authenticates a narrow tenant/client/reference projection before loading the protected request, rechecks current registration/policy and copies that exact request into a new browser-bound workflow. Its input contains only reference/client/browser correlation, so no replacement redirect, resource, scopes, objects, state or PKCE parameters can enter this transition. Both operations return raw material only after state, audit and outbox commit. The existing material source supplies independent cryptographic references/handles/CSRF values; hashes cannot be reused across their purposes.

Current registered clients are public HTTPS web clients. A matching client ID is a declaration and reference binding, not authentication or reputation. This does not implement confidential-client authentication, DPoP validation, signed request objects or a live PAR endpoint. Future adapters must authenticate confidential clients using their registered policy and derive trusted sender binding from validated proof; they cannot turn these application values into an authentication bypass.

## Consistency and persistence

Append migration 8 without altering earlier migration sources. `pushed_requests` stores only the reference hash and a bounded immutable request snapshot: client, exact redirect/audience/permission scopes, S256 challenge, sender binding, state, typed ceiling, policy version and creation/expiry. No raw reference, PKCE verifier or credential is persisted. `authorization_transactions.pushed_request_hash` retains provenance; the exact object ceiling continues through the existing storage contracts.

Each authorization transaction first holds the existing tenant coordination row FOR SHARE. Reference authorization locks the pending pushed row FOR UPDATE and its enabled client FOR SHARE, checks tenant/client/hash/policy and application/database expiry, and returns only decision metadata. The subsequent payload operation requires that transaction-local proof. Registration checks reuse the same client/resource locks. Policy and identity writers retain their conflicting tenant lock; external systems are not called while these locks are held.

Consumption atomically inserts the workflow and its audit, changes the reference from pending to used, and records the use audit/outbox. Exact stored snapshot predicates reject substitution. Unique references and workflow links admit one concurrent winner. Deferred constraint triggers reject a workflow/provenance link or a consumed reference that commits without its matching counterpart, including mismatched request snapshots. SQL reinforces exact persistence identity; domain constructors remain the owners of request/vocabulary/authority rules.

Snapshots, consumed state and workflow provenance cannot be rewritten or cleared through ordinary owner SQL. Forced RLS, tenant predicates, composite foreign keys and lifecycle-only runtime column privileges reinforce the boundary. Retention/cleanup needs a later reviewed maintenance operation; no hidden deletion or compensating cleanup is used for partial failure. The runtime is still trusted to create application state; this is not protection against a fully compromised runtime or database owner bypassing schema controls.

Apply explicit owner migrations and restart matching runtimes. Intermediate scope-only fixture rows and nullable provenance remain unfinished scaffolding, not a legacy compatibility promise. The required-flow cutover must remove these allowances and universally require validated PAR provenance/nonempty typed snapshots before the first usable P2 flow.

## Recovery, evidence and limits

Replays, foreign tenant/issuer/client references, expiry, disabled clients and changed policy fail closed. Registration changes can also deny a still-pending reference. A consumed reference cannot start a second browser workflow, including after a lost response. On timeout/uncertain commit, follow the error strategy: do not infer retry safety from a status; restart with a new pushed request when the original outcome cannot be reconciled. There is no raw-handle recovery API.

Domain/service tests cover immutable snapshots, lifetime boundaries, proof-before-payload ordering, denial before entropy, current registration changes, one use and no uncommitted material. Real PostgreSQL tests cover raw-reference absence, exact workflow snapshots, wrong-client/foreign/expired requests, policy/redirect changes, audit rollback, concurrent browser binding, snapshot replacement, deferred half-commit rejection and immutable provenance. Existing consent/issuance/replay tests run against the full additive schema.

This is application/storage support. No handler invokes it, no `request_uri` wire codec or public `I/par` route is enabled, and discovery/specification conformance claims remain unchanged. The existing browser route still rejects pushed references/RAR. Object-aware consent, codes and token issuance remain closed even for a valid pushed workflow until resource-owned authorization/display projections are connected. The next slice must add strict multi-type PAR wire selection and authorized object consent, then replace the direct scope-only route at the universally required RAR/PAR cutover. Token/refresh/introspection/SDK propagation and the BFF/resource exit demonstration remain pending. No dependency, tool, license exception or public SDK type is added.

Sources: pinned [RFC 9126](https://www.rfc-editor.org/rfc/rfc9126.html), sections 2.2, 4 and 7.1/7.3–7.5. Mayi chooses strict one-use references and explicit restart rather than the RFC's optional idempotent reload support. This storage proof is not full RFC 9126 interoperability.
